# Как опубликовать ЕГЭ-трекер на GitHub Pages

Проект подготовлен для публикации через GitHub Actions. Имя репозитория может быть любым: путь определяется автоматически. Поддерживаются адреса `https://ЛОГИН.github.io/ИМЯ-РЕПОЗИТОРИЯ/`, корневой репозиторий `ЛОГИН.github.io` и собственный домен, настроенный в GitHub Pages.

## 1. Загрузить проект

1. Распакуй ZIP на компьютере.
2. Открой свой репозиторий на GitHub.
3. Нажми **Add file → Upload files** (для пустого репозитория — **uploading an existing file**).
4. Сначала перетащи папки **`src` и `public`** и нажми внизу **Commit changes**.
5. Снова выбери **Add file → Upload files**, загрузи всё оставшееся содержимое распакованной папки и нажми **Commit changes**. Это папки `tests`, `docs`, `.github` и все файлы в корне, включая `package.json`, `package-lock.json`, `index.html`, конфигурации и файлы с точкой в начале имени.
6. Загружай файлы в основную ветку — обычно `main`.

Две порции нужны из-за ограничения браузерной загрузки GitHub — до 100 файлов за один раз. В первой порции 94 файла, вторая тоже меньше 100.

ZIP-файл загружать целиком не нужно. В архив не включены зависимости `node_modules`, готовые сборки, Git-история, служебные настройки прежнего хостинга и данные твоего браузера. GitHub установит зависимости и соберёт сайт самостоятельно.

Если GitHub предлагает открыть pull request, переключись на основную ветку репозитория перед загрузкой. Изменения в других ветках не публикуются, пока не попадут в основную.

## 2. Проверить файл автоматической публикации

В репозитории открой `.github` → `workflows` → `deploy-pages.yml`.

Проверь также наличие корневых `.prettierignore` и `.prettierrc.json`: они нужны автоматической проверке проекта.

Если папки `.github` нет, она могла пропуститься при загрузке скрытых файлов. Тогда:

1. Открой в распакованном проекте файл `.github/workflows/deploy-pages.yml` текстовым редактором.
2. На GitHub нажми **Add file → Create new file**.
3. Введи полное имя `.github/workflows/deploy-pages.yml`.
4. Вставь содержимое файла и нажми **Commit changes**.

На macOS скрытые файлы в Finder переключаются сочетанием **Command + Shift + .**. В Windows имена, начинающиеся с точки, обычно отображаются как обычные папки и файлы.

## 3. Включить GitHub Pages

1. Открой **Settings** репозитория.
2. Слева выбери **Pages**.
3. В разделе **Build and deployment → Source** выбери **GitHub Actions**.

Для бесплатного размещения личного проекта репозиторий обычно должен быть **Public**. Публичны файлы приложения; твоя история решений остаётся в браузере и сама в GitHub не отправляется.

## 4. Запустить публикацию

1. Открой вкладку **Actions**.
2. Если GitHub попросит разрешить запуск Actions в репозитории, включи их.
3. Слева выбери **Publish to GitHub Pages**.
4. Нажми **Run workflow**, выбери основную ветку и снова **Run workflow**.
5. Дождись зелёной галочки.

Если первый автоматический запуск после загрузки завершился ошибкой до включения Pages, после шага 3 запусти workflow заново. Предыдущие неудачные запуски можно оставить в истории.

Адрес сайта появится в **Settings → Pages** и в результате шага **Publish website**. Открывай этот адрес: он заканчивается именем репозитория и `/`, например `https://ivan123.github.io/ege-tracker/`. Для корневого репозитория `ivan123.github.io` путь будет `/`.

Публикация автоматически повторяется при изменениях в основной ветке. Вручную вписывать свой логин, имя репозитория или токены в код не требуется. Используются стандартные временные разрешения GitHub Actions.

## 5. Перенести историю решений

1. На прежнем сайте открой **Настройки → Экспортировать JSON** и сохрани файл.
2. На новом адресе открой **Настройки → Импортировать резервную копию**.
3. Выбери JSON, проверь состав и подтверди замену.

Перенесутся решения, подтемы и скриншоты. На новом адресе используется отдельное хранилище браузера, поэтому до импорта история будет пустой. Не загружай свою резервную копию в публичный репозиторий.

## 6. Проверить готовый сайт

- Открываются все три предмета и номера с названиями.
- Видны иллюстрации и правильно отображаются шрифты.
- Решение сохраняется и остаётся после обновления страницы.
- После первой полной загрузки в настройках появляется готовность к работе без сети.
- Если приложение предлагает обновление, сохрани открытую форму и нажми **Обновить приложение**.

## Если появилась ошибка

Открой **Actions → нужный запуск → publish** и найди красный шаг. Скопируй текст ошибки или пришли скриншот.

- Ошибка получения настроек Pages: проверь **Settings → Pages → Source: GitHub Actions** и повтори запуск.
- Ошибка публикации из другой ветки: запусти workflow из основной ветки. При изменённых правилах окружения проверь **Settings → Environments → github-pages**.
- Ошибка установки зависимостей: проверь, что загрузились и `package.json`, и `package-lock.json`.
- Не запускается автоматизация: проверь наличие `.github/workflows/deploy-pages.yml` и включённые GitHub Actions.
- Сайт показывает старую версию: дождись зелёного запуска, затем обнови приложение через его уведомление.

## Для локальной разработки

Нужен Node.js 24 (или поддерживаемая версия из `package.json`).

```sh
npm ci
npm run dev
```

Обычная сборка для корня сайта:

```sh
npm run check
```

Сборка для заданной подпапки, например `/ege-tracker/`:

```sh
npm run build -- --base=/ege-tracker/
```

Проверка подпапки и офлайн-режима в браузере:

```sh
npx playwright install chromium
npm run test:pages
```

Этот тест использует отдельную сборку `dist-pages`, строгий статический сервер на порту 4175 и отдельную папку результатов `test-results-pages`. Основная сборка `dist` не перезаписывается.

Автоматизация GitHub сначала проверяет проект, затем получает путь из `actions/configure-pages` и собирает `dist` с `BASE_PATH`. Все публичные изображения и ссылки учитывают Vite `BASE_URL`; манифест и service worker ограничены путём приложения. Кэши других проектов того же GitHub-аккаунта не удаляются.
