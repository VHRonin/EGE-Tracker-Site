# ЕГЭ Трекер — архитектура

## 1. Утверждённый стек

- **React + TypeScript** — интерфейс и типизированная логика.
- **Vite** — инструментарий проекта.
- **Tailwind CSS** — стили и адаптивность.
- **IndexedDB + Dexie.js** — постоянное локальное хранение.
- **PWA** — устанавливаемый интерфейс и кеширование необходимых статических ресурсов.
- **JSON** — переносимые резервные копии.
- **Без backend** и без обязательных сетевых сервисов.

Выбор вспомогательных библиотек (роутер, формы, графики, иконки, тесты) остаётся за исполнителем с обоснованием; избегать тяжёлых зависимостей без необходимости.

## 2. Логические слои

```text
UI (pages, components, forms, charts)
  ↓
Application (use cases: add/edit/delete, review queue, backup)
  ↓
Domain (types, pure scoring/review functions, validation)
  ↓
Data (Dexie repositories, migrations, image persistence)
```

UI не должен напрямую рассчитывать оценку знаний и формировать запросы к IndexedDB. Доменная логика — чистые функции, пригодные для модульных тестов.

Предлагаемая структура:

```text
src/
  app/              # routes, providers, navigation
  features/
    dashboard/
    subjects/
    exercises/
    attempts/
    review/
    statistics/
    backup/
  domain/           # entities, scoring, validation
  data/             # dexie schema, repositories, migrations
  shared/           # reusable UI, utilities, formatting
  styles/
```

## 3. Алгоритм оценки: версия 1

Считается для каждого номера и отдельно для каждой подтемы. В расчёте используются все записи, отсортированные по `solvedAt`, затем по стабильному идентификатору. Для каждого решения `i`:

- `r_i = 1` для правильного, иначе `0`;
- `ageDays_i = max(0, (now - solvedAt_i) / 86400000)`;
- `w_i = 2 ^ (-ageDays_i / 30)` — временной вес, половинный через 30 дней.

**Взвешенная точность:** `A = Σ(w_i * r_i) / Σ(w_i)` (от 0 до 1).

**Объём практики:** `C = min(1, N / 15)` — показатель достаточности числа решений.

**Оценка освоения:** `M = round(100 * A * (0.65 + 0.35 * C))`.

Для `N = 0`: нет оценки и статус «Не изучено». Для `N > 0`:
- `M < 40` → «Слабая подготовка»;
- `40 ≤ M < 60` → «Нужна практика»;
- `60 ≤ M < 80` → «Хорошо»;
- `M ≥ 80` → «Отлично».

**Отдельная свежесть и повторение:** `daysSinceLast = max(0, (now - max(solvedAt)) / 86400000)`.

Интервал повторения зависит от уровня и уверенности:
- `M < 40` → 2 дня;
- `40 ≤ M < 60` → 3 дня;
- `60 ≤ M < 80` → 7 дней;
- `M ≥ 80` и `C < 1` → 14 дней;
- `M ≥ 80` и `C = 1` → 30 дней.

`reviewDue = daysSinceLast >= intervalDays`. Низкая точность и малый объём дополнительно формируют рекомендации, но **не подменяют** метку просроченного повторения. Для новых номеров без решений — «Не изучено», а не просроченное повторение. Подтемы с недостаточным числом решений показывают свой уровень и рекомендацию; для общего списка повторений не дублировать номер и все его подтемы как независимые обязательные задачи без пояснения.

**Важно:** вес по календарному времени (а не только по порядку) позволяет корректно учитывать записи, внесённые задним числом. Оценка зависит от `now`; её нужно пересчитывать при открытии экрана/возврате приложения и при изменении записей. Не хранить вычисленные оценки как единственный источник истины. Параметры алгоритма вынести в конфигурацию для последующей корректировки.

### Пример

Старые ошибки и новые правильные ответы дают высокую актуальную взвешенную точность, хотя историческая общая точность ниже. Если новых попыток нет долгое время, уровень освоения не должен искусственно резко превращаться в «слабый» лишь из-за календаря: отдельно появляется «Пора повторить».

## 4. Результат по введённым ответам

Сравнивать только строки с однозначным форматом: нормализация Unicode NFC и обрезка пробелов по краям; точное совпадение. Не удалять внутренние пробелы, знаки, регистр, ведущие нули и не приводить строки к числам без отдельного согласованного правила. Если оба ответа заполнены и сравнение применимо, предлагать результат; пользователь всегда может переопределить его. Результат, подтверждённый пользователем, — источник истины. При редактировании не менять его без явного действия.

## 5. Хранение и реактивность

Dexie предоставляет таблицы, индексы и транзакции; UI получает реактивные выборки. Скриншоты — отдельные Blob-записи с MIME, размером и ссылкой из попытки. Удаление попытки и её вложений выполнять согласованно. Для массового ввода использовать транзакцию. Уникальные идентификаторы — UUID; даты — ISO 8601 UTC, показывать локально.

Схема и ограничения подробно описаны в `DATABASE.md`.

## 6. Импорт/экспорт

Формат с `schemaVersion`, `exportedAt`, массивами сущностей и изображениями в base64 с MIME. Экспорт должен быть детерминированно сериализуемым и полным. Импорт: прочитать → проверить структуру, версии, ссылки и лимиты → показать количество сущностей и размер → запросить подтверждение полной замены → выполнить замену в транзакции. При любой ошибке исходная база остаётся целой. Никаких частичных импортов. JSON не содержит исполняемого HTML; пользовательский текст выводится безопасно.

## 7. PWA и адаптивность

Манифест, иконки, кеш статических ресурсов, понятный офлайн-режим. Не кешировать пользовательские данные в service worker: их источник истины — IndexedDB. Предусмотреть проверку работы на экранах примерно от 320 px, клавиатурную навигацию, фокус и `prefers-reduced-motion`.

## 8. Качество

- Unit-тесты: scoring, review, нормализация ответов, сериализация/валидация.
- Интеграционные тесты: Dexie CRUD, миграции, импорт с откатом, вложения.
- E2E: быстрый ввод, ввод с подробностями, фильтры, сохранение после обновления страницы, экспорт→очистка→импорт.
- TypeScript strict, lint, форматирование; отсутствие сетевых зависимостей в бизнес-логике.
